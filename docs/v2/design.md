# 双文件工作流

本仓库维护长期使用的双文件规划和执行方法。`v2-*` 是兼容入口，不是发布版本；本仓库从 `0.1.0` 独立维护版本。

## 保留的契约

- `spec.md` 定义行为；`implementation-plan.md` 定义已批准的架构、所有权、接口、迁移和验证策略。
- 双文件必须 ready、版本一致且覆盖验收条件。执行者不得静默更换技术方案。
- ticket 和 goal 可以细化，不能改变上层契约。明确的用户修正需要同步到相应权威来源。
- 实现、验证、外部操作各自保留授权边界。

## 组合方式

明确的小修改可以直接执行。需要持久化决策时使用 `v2-to-spec`；需要独立交付或所有权边界时使用 `v2-to-tickets`；每张 ticket 直接用 `v2-implement` 实施和验收，不先转换 Goal。需要搬运状态时才使用 `v2-to-goal`；新会话本身不要求生成 Goal。`v2-spec-executor` 可以直接执行明确批准的双文件，不强制 fork 或特定标记。

压缩不是失败。保存权威版本、代码状态、验证证据、运行操作与下一步，恢复后核对实际状态。只有范围或状态无法可靠承接时才拆分。

## 项目规则

平台、测试命令、MCP、目录和权限留在消费项目。本仓库不包含某个 App 的私有路径或设备信息。按改动验证、复用有效结果；没有新风险或明确要求不追加全量检查。
