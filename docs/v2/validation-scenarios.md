# V2 验证收敛回归场景

这些场景用于审查入口规则和评估实际 Agent 轨迹，不是自动执行结果。静态检查只证明文件结构、引用与发布清单一致，不能证明执行效率改善。

评估时提供对应入口、最小任务材料和以下事实，检查首个实施或重试决定。记录实际轨迹与偏差，不用预期答案代替运行证据。场景不需要访问真实设备或外部服务。

| 场景与输入事实 | 应观察到的决定 | 不通过的表现 |
|---|---|---|
| `v2-to-spec`：行为要求总预算从远端接受操作起算；草案从后续等待入口计时，中间有复核 | 发布前补齐起点到消费者的传递方案，并计算复核耗时；架构未定则保持未就绪 | 因 AC 已有映射而发布矛盾双文件 |
| `v2-to-spec`：现有 fixture 名称已知，但未查明是否能模拟取消 | 标明能力待验证，并安排首个相关切片检验；不凭名称声称已具备 | 强制运行整套基线，或把未经确认的能力写成事实 |
| `v2-to-tickets`：多条行为依赖同一个未证实的事件入口 | 最早相关切片包含真实行为与入口验证，后续引用其证据；保留批准顺序，有冲突先回到计划 | 先写完所有生产层再集中测试，或每张任务重复搭宿主 |
| 两个执行入口：所选 target 不在 runner 配置中，另一个名字仅在发现列表中出现 | 在展开场景前识别验证缺口，使用配置或有效证据确认入口，并在实际运行中核对选择结果 | 反复猜 target 或把发现列表当作可执行证据 |
| 两个执行入口：两次均无连接，fixture 向公共事件流发布，consumer 读取另一条流 | 检查通道与订阅，修正投递路径后做聚焦验证 | 继续增加 sleep、换断言或重置失败计数 |
| 两个执行入口：测试声称连接挂起，但 fake 只拦截扫描，实际调用持久连接 | 核对调用分支，让 fake 控制实际方法并证明取消回收 | 改生产超时逻辑来满足未制造挂起的测试 |
| 续接：已确认某 runner 无测试 action，另有有效测试结果和仍在运行的 job | 核对输入是否变化，复用已知事实，跟踪原 job；确认终止后再重跑 | 因新会话重新尝试已排除入口，或把 RPC 超时当作进程退出 |
| 范围控制：只修 Markdown 链接；或一张 ticket 的兄弟任务未完成但并非 blocker | 文档只做适用静态检查；ticket 只完成自身行为和必要不变量 | 强制探测运行器、创建基建任务、全量测试或等待无关任务 |

## 审查落点

- 规划语义与能力可信度：`v2-to-spec` 的 Process。
- 最早切片与共享准备所有权：`v2-to-tickets` 的 Draft the graph。
- 两种执行范围：各入口的 Implement 段都在编辑前核对关键契约，先证明一个消费者路径，且文档任务豁免。
- 诊断、运行句柄与续接：两个执行入口各自的 Failure convergence 和 continuation 段；逐项对照，避免规则漂移。
- 单独安装：两个执行入口均不依赖另一个 Skill 的文件或调用，读入自身即可获得执行规则。

只有实际轨迹符合预期时，才能记录该场景的行为评估通过；文案覆盖审查与行为评估分别记录。
